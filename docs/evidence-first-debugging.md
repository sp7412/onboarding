# Evidence-First Debugging for Unfamiliar Code

**Core idea:** when a codebase is too large or unfamiliar to reason about reliably, do not let a plausible story become the diagnosis. Establish high-confidence observations, compare the failing case with a control, and require each hypothesis to explain the evidence before changing code.

This guide adapts the method in Cindy Sridharan's [How to effectively debug when you no longer understand the code](https://copyconstruct.medium.com/how-to-effectively-debug-when-you-no-longer-understand-the-code-bd3dcb2c5f7b). The article's examples are from the author's own production debugging work; the voice-agent example below is fictional.

## Five takeaways

1. **Facts before theories.** Start with reproducible behavior and high-fidelity signals, not a source-code narrative generated by a person or an agent.
2. **Always look for a control.** Compare the failure with a healthy case or another informative case that differs in a useful way.
3. **Prefer discriminating signals.** A measurement is valuable when it separates hypotheses, not merely because it correlates with the symptom.
4. **Make every hypothesis satisfy every constraint.** A theory that contradicts one reliable observation is not the root cause.
5. **Turn debugging into infrastructure.** Preserve the reproduction, add a regression test, and improve telemetry so the next investigation starts with better evidence.



For the **local log-exploration layer**, see [Operational Diagnostics & Observability](developer-tools.md#operational-diagnostics-observability) in the developer tools catalog. Log viewers can make raw events easier to navigate; they do not replace a matched control, discriminating signals, trace/span correlation, or regression verification. Treat logs as potentially sensitive evidence and redact them before sharing with external agents.

## The three-part vocabulary

| Term | Meaning | Voice-agent example |
|---|---|---|
| **Variable** | The case where the failure occurs | Calls after a deployment with elevated p99 response latency |
| **Control** | A comparison case chosen to isolate a difference | Matched calls on the prior version, with similar intent, carrier, and time window |
| **Signal** | An observation that can distinguish explanations | Per-span latency, tool retries, queue time, model/version, transfer reason, backend state |

A control need not be completely healthy. A second failure mode can be useful if it shares some conditions with the target failure while differing on a suspected cause. Record why the control is comparable and which differences remain.

## The debugging loop

### 1. Write down the observations

Start with a small evidence ledger. Mark each entry as **observed**, **inferred**, or **unknown**. Include timestamps, version/configuration, cohort, denominator, and source. Keep raw evidence separate from interpretation.

Useful evidence includes:

- trace and span timings, including queueing and time spent waiting for tools
- model, prompt, policy, tool-schema, and configuration versions
- tool success, timeout, retry, and idempotency outcomes
- telephony/provider events and turn-taking signals
- authoritative business-system state versus what the agent said happened
- deployment and feature-flag history, segmented by intent, carrier, and customer configuration

Do not treat missing telemetry as proof that an event did not occur. It may mean the event was not instrumented, was sampled out, or happened outside the component being observed.

### 2. Choose a control and find the difference

Compare matching windows and cohorts. Avoid comparing a post-deployment slice with a broad aggregate that includes pre-deployment traffic. Check whether the input mix changed before attributing an aggregate regression to the implementation.

Ask: **What is different between the variable and the control that could explain the symptom?** Look beyond the first dashboard: a downstream latency increase may originate in client routing, queueing, retries, context assembly, or another upstream dependency.

### 3. Maintain competing hypotheses

Keep the list short and falsifiable. For each hypothesis, state:

- the mechanism that would produce the symptom
- evidence that supports it
- evidence that contradicts it
- the next measurement that best distinguishes it from alternatives
- what result would cause you to reject it

Do not confuse confidence with plausibility. A hypothesis supported only by the fact that it sounds like a familiar bug should remain weak.

### 4. Validate against every constraint

A leading hypothesis must account for all high-confidence observations, not just the most salient one. If it fails, revise it. If every hypothesis fails, collect another signal or reconsider the framing rather than inventing assumptions.

Code inspection, history, and bisecting are useful tools, but use them to explain the observed behavior. Reading code alone can produce a detailed, coherent, incorrect story.

### 5. Verify the fix and improve the system

- Reproduce the original failure when feasible, and preserve a minimal fixture.
- Make the smallest change that addresses the demonstrated mechanism.
- Run the regression case and adjacent tests; check safety and performance constraints.
- Verify the external outcome against authoritative state, not just the model's explanation.
- Record remaining uncertainty and avoid claiming a confirmed root cause before evidence supports it.
- Add missing telemetry, a targeted test, or a reusable diagnostic query so the same class of failure is easier to investigate next time.

For production incidents, containment and customer impact come first; the evidence loop must not delay a justified rollback or safe fallback. Establish decision thresholds in advance, and investigate without making unauthorized production changes.

## Worked example: p99 latency rises after a voice-agent deployment

All numbers and systems in this scenario are fictional.

### Initial observations

- p99 end-to-end response latency rises after a release.
- Aggregate model latency and backend error rate look unchanged.
- Human-transfer rate also rises.
- No single component has yet been shown to explain the extra latency.

These observations do **not** prove that the model is slow or that the release caused the regression. First align the time window with the deployment and segment by intent, carrier, model version, and configuration.

### Hypothesis matrix

| Hypothesis | Evidence that would support it | Discriminating next check |
|---|---|---|
| Model generation slowed | Increased model span duration in affected calls | Compare model time by version and matched intent |
| Tool calls are retrying | More attempts, timeouts, or backoff per logical operation | Compare tool-attempt counts and retry reasons |
| Orchestration queueing increased | Queue/wait spans grow while component execution times stay flat | Compare queue time and concurrency by cohort |
| Input mix became harder | More complex intents or longer context in the affected window | Compare within-intent results, not just aggregate rates |
| Provider or transport changed | Delay correlates with carrier/provider or connection events | Compare matched calls by carrier and transport events |

Suppose the model and backend spans remain stable, but orchestration wait time rises only for one cohort. That result weakens the first two hypotheses and directs the next investigation toward concurrency, scheduling, or cohort-specific dependencies. It is still a lead, not a confirmed root cause; gather the next signal and verify the mechanism.

### Example evidence record

Use a compact record that can be attached to an incident or evaluation case:

    {
      "case_id": "voice-latency-017",
      "environment": "fictional-staging",
      "version": "release-b",
      "control_version": "release-a",
      "symptom": "p99_response_latency_regression",
      "observations": [
        {
          "signal": "model_span_ms",
          "comparison": "unchanged",
          "status": "observed"
        },
        {
          "signal": "orchestration_wait_ms",
          "comparison": "higher_in_affected_cohort",
          "status": "observed"
        }
      ],
      "hypotheses": [
        {
          "claim": "orchestration queueing drives the regression",
          "status": "unconfirmed",
          "next_test": "compare queue depth and concurrency by cohort"
        }
      ],
      "decision": "collect_more_evidence"
    }

This is a teaching shape, not a production schema. In real telemetry, include stable trace/span IDs, timestamps, cohort definitions, sample sizes, measurement units, and version identifiers. Do not put secrets, raw caller PII, or unnecessary transcript content in the record.

## Using coding agents safely

Treat the agent as an investigator that proposes measurements and explanations, not as the authority that declares a root cause.

Give it read-only access to the minimum necessary diagnostic data. Require it to:

1. quote or reference the observations supporting each claim;
2. distinguish facts, inferences, and unknowns;
3. compare the failing case with a stated control;
4. propose a measurement that could disprove its leading hypothesis;
5. retract or revise explanations that contradict evidence;
6. request approval before changing code or taking production actions.

A second agent reviewing the first agent's reasoning can help, but agreement is not independent evidence if both agents rely on the same faulty assumptions. Ask the reviewer to search specifically for contradictions, missing controls, and untested premises.

## Practice exercise

Use the fictional incident in [Production Incident Simulation](../senior-engineer/production-incident.md).

Before proposing a fix, produce:

- an evidence ledger with at least five observed facts and explicit unknowns;
- a justified control and the cohort dimensions that must match;
- five competing hypotheses, each with a discriminating next test;
- a hypothesis/evidence matrix that includes contradictory evidence;
- a containment decision and rollback criteria;
- a regression test or evaluation case, plus one telemetry improvement.

**Self-check:** a strong diagnosis explains all reliable observations, survives a meaningful attempt to falsify it, and has a verification plan tied to the original symptom. If evidence is insufficient, the correct conclusion is that the root cause remains unknown.
